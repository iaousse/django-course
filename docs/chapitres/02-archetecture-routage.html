Où en sommes-nous ?

Au chapitre précédent, nous avons obtenu un projet qui démarre, une app cours déclarée dans INSTALLED_APPS et un dépôt Git propre. L’app est encore vide : aucune page n’existe en dehors de la fusée de Django. Ce chapitre construit les routes (qui répondent à « quelle URL mène à quel code ? ») et les premières vues, sans base de données ni HTML : nous voulons comprendre le mécanisme avant d’ajouter des couches.

Le chemin complet d’une requête

Une bonne application Django n’est pas une collection de fichiers que l’on modifie au hasard. Elle est une chaîne de responsabilités. Pour une requête vers /cours/python-pour-debutants/, le parcours conceptuel est :

navigateur
   │  requête HTTP
   ▼
config/urls.py
   │  route choisie
   ▼
vue Python
   │  lecture ou écriture
   ▼
modèle / ORM ─── base de données
   │
   ▼
template ─── contexte Python
   │  HTML
   ▼
navigateur

Django appelle souvent cette organisation MVT (Modèle–Vue–Template) :

Élément Django Responsabilité Analogie MVC
Model données, contraintes et accès à la base Model
View traitement de la requête et choix de la réponse Controller
Template représentation HTML View

La comparaison avec MVC est utile mais imparfaite : le mot « vue » désigne dans Django ce que d’autres frameworks appellent un contrôleur. Le nom importe moins que la règle : une vue ne devrait pas contenir tout le HTML, un template ne devrait pas interroger directement la base, et un modèle ne devrait pas connaître la mise en page. Le découpage rend chaque partie remplaçable et testable (Django Software Foundation 2025). Les bonnes pratiques de conception Django insistent aussi sur la lisibilité, la simplicité et le respect des conventions du framework (Greenfeld et Roy Greenfeld 2017).

À quelle couche appartient ce code ?

Face à une règle ou à un morceau de code, demandez-vous où le ranger :

Si cela concerne… Cela va dans… Exemple dans BiblioCours
la forme des données et leurs contraintes le modèle un slug est unique
la décision à prendre pour une requête la vue n’afficher que les cours publiés
la mise en page HTML le template la carte d’un cours
quelle URL mène où le routeur (urls.py) /cours/<slug>/
la validation d’une saisie le formulaire (chapitre 5) titre de 5 caractères minimum

Quelques notions HTTP indispensables

Deux informations accompagnent chaque échange : la méthode de la requête et le code de statut de la réponse.

Méthode Usage habituel Modifie des données ?
GET lire une page non
POST envoyer un formulaire, déclencher une action oui
Statut Signification Exemple
200 OK succès la page s’affiche
301 / 302 redirection permanente / temporaire après un formulaire valide
403 Forbidden identifié (ou non) mais interdit permission manquante
404 Not Found ressource inconnue slug qui n’existe pas
405 Method Not Allowed méthode non acceptée GET sur une vue réservée à POST
500 Internal Server Error erreur dans le code serveur exception non gérée

Retenez la famille du premier chiffre : 2xx succès, 3xx redirection, 4xx erreur du client (la requête est incorrecte), 5xx erreur du serveur (le code est en cause). Cette lecture vous aidera à savoir où chercher.

Les apps : découper par responsabilité

L’app cours aura les responsabilités liées au catalogue pédagogique. Dans une application qui grandit, on pourrait ajouter :

comptes/        utilisateurs, profils, permissions
cours/          matières et cours
inscriptions/   suivi de la progression
notifications/  courriels et alertes

Une app bien découpée peut être déplacée dans un autre projet avec peu de modifications. Il ne faut pas créer une app pour chaque modèle : on crée une app pour un domaine fonctionnel cohérent. Ici, Matiere et Cours forment ensemble un seul domaine, le catalogue : une seule app suffit.

Lire settings.py plutôt que le copier

Le fichier config/settings.py configure le comportement du projet. Ce n’est pas un fichier à mémoriser, mais à savoir lire. Voici ses sections importantes, dans l’ordre :

from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

SECRET_KEY = "à-remplacer-en-production"
DEBUG = True
ALLOWED_HOSTS = []

INSTALLED_APPS = [
    # Apps Django fournies
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    # App du projet
    "cours",
]

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]

ROOT_URLCONF = "config.urls"

TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [],
        "APP_DIRS": True,
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
        },
    },
]

WSGI_APPLICATION = "config.wsgi.application"

Passons-les en revue :

  • BASE_DIR est le dossier racine du projet. On construit les autres chemins à partir de lui, pour que le projet fonctionne quel que soit son emplacement ;
  • INSTALLED_APPS active les composants ;
  • MIDDLEWARE forme une pile traversée par les requêtes et les réponses (voir l’encadré ci-dessous) ;
  • ROOT_URLCONF indique quel routeur commencer à lire ;
  • TEMPLATES indique comment trouver et rendre les templates ;
  • WSGI_APPLICATION désigne le point d’entrée pour les serveurs de production.
AstuceLes middlewares : une pelure d’oignon

Chaque middleware est une couche qui enveloppe la vue. La requête traverse les couches de haut en bas de la liste avant d’atteindre la vue ; la réponse les retraverse de bas en haut.

requête  →  Security → Session → Common → Csrf → Auth → … → VUE
réponse  ←  Security ← Session ← Common ← Csrf ← Auth ← … ← VUE

C’est ainsi que request.user existe dans toutes les vues (grâce à SessionMiddleware et AuthenticationMiddleware) et que les formulaires sont protégés contre le CSRF (grâce à CsrfViewMiddleware). L’ordre compte : un middleware peut dépendre de ce qu’un autre a préparé avant lui.

Ce qui se trouve plus bas dans le fichier

Trois autres réglages produits par startproject méritent un regard :

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}

LANGUAGE_CODE = "en-us"
TIME_ZONE = "UTC"
USE_TZ = True

STATIC_URL = "static/"
  • DATABASES indique quelle base utiliser. Par défaut, SQLite, un simple fichier db.sqlite3 : idéal pour apprendre, car il n’y a rien à installer ;
  • LANGUAGE_CODE détermine la langue des messages de Django (erreurs de formulaire, administration) ;
  • TIME_ZONE et USE_TZ gèrent les dates. Avec USE_TZ = True, Django stocke les dates en UTC dans la base et les convertit dans le fuseau configuré à l’affichage ;
  • STATIC_URL est le préfixe des fichiers CSS et JavaScript (voir Authentification, sécurité et fichiers statiques).

Pour que BiblioCours parle français, modifiez :

LANGUAGE_CODE = "fr"
TIME_ZONE = "Europe/Paris"  # remplacez par votre fuseau horaire

Redémarrez le serveur et ouvrez /admin/ : la page de connexion est désormais en français.

Le secret et le mode debug

SECRET_KEY est utilisé par plusieurs mécanismes cryptographiques de Django (signature des sessions, des jetons CSRF…). Il ne doit pas être publié. DEBUG = True affiche des informations très détaillées en cas d’erreur ; c’est utile localement et dangereux sur Internet. ALLOWED_HOSTS liste les noms de domaine que Django accepte de servir ; vide, il n’accepte que localhost et 127.0.0.1 tant que DEBUG est actif. Nous apprendrons à protéger ces trois réglages au Authentification, sécurité et fichiers statiques, et à les configurer pour la production au Préparer la production et continuer l’apprentissage.

Déclarer les premières routes

Le routeur principal reçoit une liste de motifs. Modifiez config/urls.py :

from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("cours/", include("cours.urls")),
]

Créez ensuite cours/urls.py :

from django.urls import path

from . import views

app_name = "cours"

urlpatterns = [
    path("", views.accueil, name="accueil"),
]

La fonction path(route, vue, name=...) associe un motif à une vue. Trois détails sont essentiels :

  1. include délègue un préfixe à l’app : toute URL commençant par cours/ est confiée à cours/urls.py, qui ne voit alors que la suite du chemin ;
  2. app_name crée un espace de noms : la route s’appellera cours:accueil, pas simplement accueil ;
  3. name donne un identifiant stable à la route.

Un template doit utiliser le nom de la route, pas recopier son URL. Ainsi, si cours/ devient catalogue/, les liens générés par {% url %} restent cohérents après la modification du routeur.

NotePourquoi tous ces / finaux ?

Django a l’habitude de terminer les URLs par /. Si vous demandez /cours (sans le / final), CommonMiddleware répond par une redirection vers /cours/. Cela évite que deux adresses différentes présentent la même page, ce que les moteurs de recherche n’apprécient pas. Écrivez donc toujours vos routes avec un / final.

Écrire une vue minimale

Dans cours/views.py :

from django.http import HttpRequest, HttpResponse


def accueil(request: HttpRequest) -> HttpResponse:
    return HttpResponse("Bienvenue dans BiblioCours")

Démarrez le serveur et ouvrez http://127.0.0.1:8000/cours/. Vous devriez voir le message. Une vue est une simple fonction qui reçoit au minimum un objet HttpRequest et renvoie un objet de réponse. HttpResponse est idéal pour comprendre le mécanisme, mais une application HTML utilisera plutôt render, présenté au Construire les pages : vues, URLs et templates.

Observez le journal du terminal : une ligne "GET /cours/ HTTP/1.1" 200 … confirme que la requête est arrivée, a été routée et a produit un 200.

Paramètres capturés dans l’URL

Django sait convertir une partie de l’URL avant d’appeler la vue. Ajoutez une route de détail à cours/urls.py :

urlpatterns = [
    path("", views.accueil, name="accueil"),
    path("<slug:slug>/", views.detail_cours, name="detail"),
]

La syntaxe <convertisseur:nom> capture un segment de l’URL et le transmet à la vue comme argument nommé. Pour /cours/python-pour-debutants/, Django appelle detail_cours(request, slug="python-pour-debutants"). Ajoutez la vue :

def detail_cours(request: HttpRequest, slug: str) -> HttpResponse:
    return HttpResponse(f"Le cours demandé est : {slug}")

Le nom entre chevrons doit correspondre exactement au nom du paramètre de la vue. Les convertisseurs disponibles sont :

Convertisseur Accepte Exemple de segment valide Valeur Python
str tout texte sans / (défaut) bonjour str
int entiers positifs ou nuls 12 int
slug lettres, chiffres, - et _ python-pour-debutants str
uuid un UUID formaté 075194d3-6885-417e-a8a8-6c931e272f00 UUID
path texte avec des / docs/guide/intro str

Un segment qui ne correspond pas au convertisseur n’est pas une erreur de la vue : la route ne correspond simplement pas, et Django essaie la suivante, puis renvoie une 404 s’il n’en reste aucune. Une URL porte donc une information structurée, et non une chaîne que la vue doit parser elle-même.

AstuceQuestion de conception

Le projet utilisera un slug (/cours/python-pour-debutants/) plutôt qu’un identifiant entier (/cours/12/). L’URL est plus lisible, plus parlante pour un moteur de recherche et ne révèle pas le nombre de cours. L’identifiant entier, lui, est plus compact et immuable. Le choix de l’URL est à la fois une décision technique, une décision d’ergonomie et une décision de référencement.

Comprendre la résolution des URLs

Django parcourt urlpatterns de haut en bas et s’arrête au premier motif correspondant. L’ordre compte. Ajoutons une page statique « À propos » :

urlpatterns = [
    path("", views.accueil, name="accueil"),
    path("a-propos/", views.a_propos, name="a_propos"),
    path("<slug:slug>/", views.detail_cours, name="detail"),
]

et sa vue :

def a_propos(request: HttpRequest) -> HttpResponse:
    return HttpResponse("BiblioCours est un projet d'apprentissage de Django.")

La route statique a-propos/ précède la route dynamique <slug:slug>/. Si vous inversiez l’ordre, le mot a-propos serait un slug valide : la route dynamique le capturerait et la page « À propos » deviendrait inaccessible.

AvertissementExpérience à faire

Échangez temporairement l’ordre de a-propos/ et de <slug:slug>/ dans cours/urls.py, puis ouvrez /cours/a-propos/. Que voyez-vous ? Remettez ensuite l’ordre correct. Retenez la règle : les routes les plus spécifiques d’abord, les routes génériques ensuite.

Corollaire : un cours dont le slug vaudrait a-propos serait inaccessible. Nous reviendrons sur ce piège quand nous validerons les slugs (Saisir et administrer les données : formulaires et admin).

Fabriquer une URL : reverse et les noms de routes

Pour obtenir une URL depuis son nom, ouvrez le shell Django :

uv run python manage.py shell
from django.urls import reverse

reverse("cours:a_propos")
# "/cours/a-propos/"

reverse("cours:detail", kwargs={"slug": "python-pour-debutants"})
# "/cours/python-pour-debutants/"

Cette technique est préférable à "/cours/a-propos/" écrit en dur : si le préfixe cours/ change dans config/urls.py, tous les liens suivent automatiquement. Elle sert notamment dans les redirections, les modèles (get_absolute_url) et les tests. Dans un template, l’équivalent est la balise {% url 'cours:a_propos' %}.

Le préfixe cours: (l’espace de noms défini par app_name) évite les collisions : si une autre app définissait aussi une route accueil, on distinguerait cours:accueil et autre:accueil.

Si vous donnez de mauvais arguments, Django lève NoReverseMatch. Essayez reverse("cours:detail", kwargs={"pk": 1}) : le message d’erreur indique le nom des paramètres attendus. Apprenez à lire ces messages, ils sont précis.

Un premier test automatique

Nous allons vérifier nos routes par un test. startapp a créé un fichier cours/tests.py. Comme nous aurons plusieurs fichiers de tests, remplacez-le par un paquet :

rm cours/tests.py
mkdir cours/tests
touch cours/tests/__init__.py

(Un fichier tests.py et un dossier tests/ ne peuvent pas coexister : Python ne saurait pas lequel importer.) Créez cours/tests/test_urls.py :

from django.test import SimpleTestCase
from django.urls import resolve, reverse

from cours import views


class RoutesTests(SimpleTestCase):
    def test_reverse_a_propos(self):
        self.assertEqual(reverse("cours:a_propos"), "/cours/a-propos/")

    def test_a_propos_repond_200(self):
        response = self.client.get(reverse("cours:a_propos"))

        self.assertEqual(response.status_code, 200)

    def test_a_propos_n_est_pas_capturee_par_le_detail(self):
        correspondance = resolve("/cours/a-propos/")

        self.assertEqual(correspondance.func, views.a_propos)

Lancez-les :

uv run python manage.py test

Trois éléments sont nouveaux : self.client simule un navigateur sans lancer de serveur ; resolve fait l’opération inverse de reverse (de l’URL vers la vue) ; SimpleTestCase est la classe de test la plus légère, qui interdit tout accès à la base de données. Le Tester, diagnostiquer et faire évoluer le code détaillera les autres classes de test. Le troisième test est précieux : il échouerait si quelqu’un inversait l’ordre des routes.

Requêtes et réponses : les distinctions importantes

Une requête contient plusieurs catégories d’information :

def rechercher(request):
    terme = request.GET.get("q", "")
    langue = request.headers.get("Accept-Language")
    utilisateur = request.user
    return HttpResponse(
        f"Recherche : {terme}",
        content_type="text/plain; charset=utf-8",
    )
Attribut Contenu Remarque
request.method "GET", "POST"… décide de l’action à mener
request.GET paramètres de l’URL (?q=django) données de lecture, saisies par l’utilisateur
request.POST données d’un formulaire envoyé saisies par l’utilisateur
request.user utilisateur courant, éventuellement anonyme fourni par un middleware
request.headers en-têtes HTTP décrivent le contexte, non fiables
request.path chemin demandé

Une vue ne doit pas faire confiance aux données reçues. Même un champ qui semble numérique ou une valeur provenant d’un navigateur doit être validé côté serveur. Les formulaires Django aideront à centraliser cette validation.

Remarquez le content_type="text/plain" dans l’exemple ci-dessus. Par défaut, une HttpResponse est du HTML : si l’on y recopiait terme tel quel et que l’utilisateur tapait <script>…</script>, le navigateur l’exécuterait (c’est une faille XSS, étudiée au Authentification, sécurité et fichiers statiques). En déclarant la réponse comme du texte brut, le navigateur n’interprète rien. Les templates, eux, échappent automatiquement les variables.

Pour construire une réponse, HttpResponse(contenu, status=200, content_type=...) accepte aussi un statut explicite. Pour signaler une page inexistante, on lèvera plutôt Http404 (from django.http import Http404), que Django transforme en réponse 404.

Premier modèle mental à retenir

Quand une page ne fonctionne pas, diagnostiquez dans cet ordre :

  1. l’URL est-elle réellement atteinte ?
  2. la vue est-elle appelée avec les bons paramètres ?
  3. la requête vers la base renvoie-t-elle le résultat attendu ?
  4. le contexte transmis au template porte-t-il le bon nom ?
  5. le template affiche-t-il ce nom et cette valeur ?
  6. le navigateur reçoit-il le HTML attendu ?

Cette méthode est plus rapide que de modifier simultanément le modèle, la vue, le template et le CSS. Deux outils aident déjà aux étapes 1 et 2 : le journal du terminal (la requête est-elle arrivée ? quel statut ?) et la page 404 de débogage de Django, qui, en mode DEBUG, liste toutes les routes qu’elle a essayées dans l’ordre.

Symptôme Cause probable Remède

À retenir

  • Le chemin est : navigateur → routeur → vue → (modèle) → template → navigateur.
  • Le routeur lit les motifs dans l’ordre et s’arrête au premier qui correspond : le spécifique avant le générique.
  • include délègue, app_name isole, name identifie.
  • On fabrique les URLs avec reverse (Python) ou {% url %} (template), jamais à la main.
  • Les données d’une requête (GET, POST, en-têtes) viennent de l’extérieur : on les valide toujours.
  • Un code de statut en 4xx oriente vers le client, en 5xx vers le serveur.
