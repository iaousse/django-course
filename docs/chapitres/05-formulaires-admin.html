Où en sommes-nous ?

BiblioCours affiche son catalogue (chapitre 4), mais pour ajouter un cours il faut passer par le shell. Dans ce chapitre, nous construisons deux outils de saisie complémentaires :

  • des formulaires publics, par lesquels un éditeur crée et modifie des brouillons ;
  • l’administration Django, par laquelle une personne habilitée relit et publie les cours.

Ce partage des rôles est une décision de conception : un éditeur qui rédige ne publie pas lui-même, et le formulaire ne propose donc pas le champ statut.

Pourquoi un formulaire HTML ne suffit pas

Un formulaire est une frontière entre le navigateur et l’application. Le navigateur peut aider avec required, type="email" ou maxlength, mais ces attributs ne sont pas des protections : n’importe quel client HTTP (un script, l’outil curl, un navigateur modifié) peut les contourner. La validation importante doit être exécutée côté serveur.

Django distingue trois étapes :

  1. liaison : associer les données reçues à un formulaire ;
  2. validation : vérifier les champs et les règles métier ;
  3. action : sauvegarder ou effectuer une opération seulement si le formulaire est valide.

Un formulaire non valide doit être réaffiché avec les valeurs acceptables et les erreurs lisibles. Un formulaire valide doit éviter de créer deux fois la même ressource lorsque l’utilisateur actualise la page. Ce dernier problème est résolu par le schéma POST/Redirect/GET (PRG) :

1. GET  /cours/nouveau/     → le serveur renvoie le formulaire vide        (200)
2. POST /cours/nouveau/     → données invalides : formulaire réaffiché     (200)
3. POST /cours/nouveau/     → données valides : sauvegarde, puis redirection (302)
4. GET  /cours/<slug>/modifier/ → le navigateur suit la redirection       (200)

Sans l’étape 3, l’utilisateur qui actualise la page après un succès renverrait le POST et créerait un doublon. Avec la redirection, l’actualisation répète seulement le GET de l’étape 4, qui est inoffensif.

Les deux états d’un formulaire

Un formulaire Django existe sous deux formes :

État Création is_valid() Usage
non lié (unbound) CoursForm() toujours False afficher un formulaire vide ou pré-rempli
lié (bound) CoursForm(request.POST) valide les données traiter une soumission

Une fois is_valid() appelé, deux attributs deviennent disponibles : form.cleaned_data (les valeurs validées et converties en types Python) et form.errors (les messages d’erreur par champ).

Créer un ModelForm

Créez cours/forms.py :

from django import forms

from .models import Cours


class CoursForm(forms.ModelForm):
    class Meta:
        model = Cours
        fields = ["titre", "slug", "resume", "contenu", "matiere"]
        widgets = {
            "resume": forms.Textarea(attrs={"rows": 3}),
            "contenu": forms.Textarea(attrs={"rows": 12}),
        }

    def clean_titre(self):
        titre = self.cleaned_data["titre"].strip()
        if len(titre) < 5:
            raise forms.ValidationError(
                "Le titre doit comporter au moins cinq caractères."
            )
        return titre

    def clean(self):
        cleaned_data = super().clean()
        titre = cleaned_data.get("titre")
        resume = cleaned_data.get("resume")
        if titre and resume and titre.lower() in resume.lower():
            self.add_error(
                "resume",
                "Le résumé ne doit pas répéter le titre mot pour mot.",
            )
        return cleaned_data

ModelForm déduit les champs à partir du modèle et réutilise ses contraintes de base (longueur maximale, unicité, champ obligatoire). La liste fields doit être explicite : fields = "__all__" risque d’exposer un champ ajouté plus tard sans que l’on s’en rende compte (Django Software Foundation 2025).

Notre liste omet volontairement statut et date_publication. Même si un utilisateur malveillant ajoutait statut=publie à la requête POST, Django ignorerait ce champ inconnu : un éditeur ne peut pas se publier lui-même. C’est une protection très concrète contre les modifications non autorisées de champs sensibles.

Les niveaux de validation

Quand on appelle is_valid(), Django enchaîne les validations dans cet ordre :

  1. par champ : conversion et contraintes de base (obligatoire, longueur, format) ;
  2. clean_<champ>() : règle propre à un champ (clean_titre) ;
  3. clean() du formulaire : règle qui compare plusieurs champs ;
  4. validation du modèle : Model.clean() (notre règle sur la date de publication) et contraintes d’unicité (slug unique).

Chaque méthode a un rôle précis :

  • clean_titre valide un champ et se concentre sur sa valeur ; elle doit renvoyer la valeur nettoyée ;
  • clean valide une relation entre plusieurs champs ; on y accède aux champs déjà validés via cleaned_data.get(...) (un champ invalide peut manquer) ;
  • Model.clean porte une règle de modèle indépendante de ce formulaire.

Une validation ne doit pas seulement servir à afficher un message. Elle doit protéger l’invariant métier. Par exemple, si un cours publié doit toujours avoir un résumé, cette règle devrait être appliquée dans tous les chemins de création, pas uniquement sur la page HTML : on la place dans le modèle (voir l’exercice 7 du Modéliser les données avec l’ORM et les migrations).

La vue de création

Ajoutez la route à cours/urls.py. Elle doit précéder la route générique <slug:slug>/, sans quoi nouveau serait traité comme le slug d’un cours. Voici la liste complète des routes à ce stade, qui inclut aussi celles de modification et de suppression :

urlpatterns = [
    path("", views.liste_cours, name="liste"),
    path("a-propos/", views.a_propos, name="a_propos"),
    path("nouveau/", views.creer_cours, name="creer"),
    path("matiere/<slug:slug>/", views.cours_par_matiere, name="par_matiere"),
    path("<slug:slug>/", views.detail_cours, name="detail"),
    path("<slug:slug>/modifier/", views.modifier_cours, name="modifier"),
    path("<slug:slug>/supprimer/", views.supprimer_cours, name="supprimer"),
]

Puis, dans cours/views.py, ajoutez les imports et la vue :

from django.contrib import messages
from django.contrib.auth.decorators import login_required
from django.shortcuts import get_object_or_404, redirect, render

from .forms import CoursForm


@login_required
def creer_cours(request):
    if request.method == "POST":
        form = CoursForm(request.POST)
        if form.is_valid():
            cours = form.save()
            messages.success(
                request, f"Le brouillon « {cours.titre} » a été créé."
            )
            return redirect("cours:modifier", slug=cours.slug)
    else:
        form = CoursForm()

    contexte = {"form": form, "titre_page": "Créer un cours"}
    return render(request, "cours/formulaire.html", contexte)

La méthode HTTP est une décision de sécurité et de sémantique :

  • GET affiche le formulaire et ne doit pas modifier l’état ;
  • POST transmet une intention de modification ;
  • une redirection après succès empêche un rafraîchissement de répéter le POST.

Remarquez la structure if POST … else GET : si le formulaire est invalide, on ne redirige pas, on laisse la vue atteindre le render final avec le formulaire lié, qui contient les valeurs saisies et les erreurs.

ImportantPourquoi rediriger vers la page de modification et non vers le détail ?

Un cours fraîchement créé est un brouillon, et detail_cours ne montre que les cours publiés : rediriger vers cours.get_absolute_url() mènerait à une 404. On redirige donc vers cours:modifier, qui existe quel que soit le statut. La destination d’une redirection doit toujours être une page que l’utilisateur peut effectivement voir.

Le décorateur login_required redirige les utilisateurs anonymes vers la page de connexion. Nous verrons la configuration de cette redirection, et son remplacement par un contrôle de permission, au Authentification, sécurité et fichiers statiques.

NoteTester sans page de connexion

La page de connexion n’existe pas encore (elle arrive au chapitre 6), donc un visiteur anonyme est redirigé vers /accounts/login/, qui renvoie une 404 : c’est attendu. Pour tester vos vues dès maintenant, connectez-vous par l’administration (/admin/, après createsuperuser, voir plus bas). La session ouverte est partagée par tout le site.

Le template du formulaire

cours/templates/cours/formulaire.html :

{% extends "cours/base.html" %}

{% block title %}{{ titre_page }} — BiblioCours{% endblock %}

{% block content %}
  <h1>{{ titre_page }}</h1>

  <form method="post" novalidate>
    {% csrf_token %}

    {% if form.non_field_errors %}
      <div class="errors" role="alert">
        {{ form.non_field_errors }}
      </div>
    {% endif %}

    {% for field in form %}
      <div class="form-field">
        {{ field.label_tag }}
        {{ field }}
        {% if field.help_text %}
          <p class="help">{{ field.help_text }}</p>
        {% endif %}
        {% for error in field.errors %}
          <p class="error" role="alert">{{ error }}</p>
        {% endfor %}
      </div>
    {% endfor %}

    <button type="submit">Enregistrer</button>
    <a href="{% url 'cours:liste' %}">Annuler</a>
    {% if cours %}
      <a href="{% url 'cours:supprimer' cours.slug %}">Supprimer</a>
    {% endif %}
  </form>
{% endblock %}

Ce template sert à la création et à la modification : seul le titre de la page (titre_page) et la présence de cours dans le contexte changent. Le parcours {% for field in form %} donne un contrôle fin sur le rendu, mais on peut aussi écrire simplement { form.as_p } pour un rendu rapide.

{% csrf_token %} est obligatoire pour un POST provenant d’un formulaire Django. Le jeton associe la requête à la session et protège contre une partie des attaques CSRF (Authentification, sécurité et fichiers statiques). Il ne remplace ni l’authentification ni l’autorisation. Sans lui, le POST est refusé avec une erreur 403.

novalidate désactive la validation native du navigateur afin de rendre visibles les messages Django pendant l’apprentissage. Dans un projet réel, vous pouvez conserver la validation native en complément ; elle améliore l’expérience mais ne remplace jamais la validation serveur.

Modifier un objet existant

Le même ModelForm peut être lié à une instance :

@login_required
def modifier_cours(request, slug):
    cours = get_object_or_404(Cours, slug=slug)

    if request.method == "POST":
        form = CoursForm(request.POST, instance=cours)
        if form.is_valid():
            cours = form.save()
            messages.success(request, "Le cours a été mis à jour.")
            if cours.est_publie:
                return redirect(cours)
            return redirect("cours:modifier", slug=cours.slug)
    else:
        form = CoursForm(instance=cours)

    contexte = {"form": form, "cours": cours, "titre_page": "Modifier le cours"}
    return render(request, "cours/formulaire.html", contexte)

La présence d’instance change le comportement : sans elle, save() crée un objet ; avec elle, save() met à jour l’objet. La vue utilise ici get_object_or_404(Cours, slug=slug) : à la différence de la page publique, elle accepte aussi les brouillons, puisqu’on veut pouvoir les éditer.

Après un succès, deux cas se présentent : un cours publié renvoie vers sa page publique (redirect(cours) utilise automatiquement get_absolute_url), un brouillon revient sur le formulaire. La route de modification doit être distincte de la route de création et doit vérifier que l’utilisateur a le droit de modifier ce cours : ce contrôle d’autorisation sera ajouté au Authentification, sécurité et fichiers statiques.

Supprimer : préférer une confirmation explicite

La suppression ne devrait pas être déclenchée par un lien GET :

<!-- À éviter : un robot ou un clic involontaire pourrait supprimer -->
<a href="{% url 'cours:supprimer' cours.slug %}">Supprimer</a>

Un lien GET est suivi par les robots d’indexation, préchargé par certains navigateurs et déclenché par un simple clic distrait. On affiche donc d’abord une page de confirmation (en GET, inoffensive), et c’est le formulaire POST de cette page, protégé par le jeton CSRF, qui supprime vraiment :

@login_required
def supprimer_cours(request, slug):
    cours = get_object_or_404(Cours, slug=slug)
    if request.method == "POST":
        titre = cours.titre
        cours.delete()
        messages.success(request, f"Le cours « {titre} » a été supprimé.")
        return redirect("cours:liste")
    return render(request, "cours/confirmer_suppression.html", {"cours": cours})

cours/templates/cours/confirmer_suppression.html :

{% extends "cours/base.html" %}

{% block title %}Supprimer — BiblioCours{% endblock %}

{% block content %}
  <h1>Supprimer « {{ cours.titre }} » ?</h1>
  <p>Cette action est définitive.</p>
  <form method="post">
    {% csrf_token %}
    <button type="submit">Oui, supprimer</button>
    <a href="{% url 'cours:modifier' cours.slug %}">Annuler</a>
  </form>
{% endblock %}

L’approbation visuelle n’est pas une mesure de sécurité ; l’autorisation et le POST protégé le sont. Une opération irréversible doit aussi être reflétée dans les tests et, selon le domaine, dans une stratégie d’archivage plutôt que de suppression physique.

L’administration Django

L’admin est une interface interne puissante pour les personnes qui gèrent le contenu. Elle ne remplace pas une interface publique : ses écrans, ses permissions et son modèle mental sont ceux d’un back-office. Elle permet néanmoins de peupler BiblioCours rapidement et de publier les brouillons.

Dans cours/admin.py :

from django.contrib import admin, messages
from django.utils import timezone

from .models import Cours, Matiere


@admin.register(Matiere)
class MatiereAdmin(admin.ModelAdmin):
    list_display = ["nom", "slug"]
    search_fields = ["nom", "description"]
    prepopulated_fields = {"slug": ("nom",)}


@admin.register(Cours)
class CoursAdmin(admin.ModelAdmin):
    list_display = [
        "titre",
        "matiere",
        "statut",
        "date_creation",
        "date_publication",
    ]
    list_filter = ["statut", "matiere", "date_creation"]
    search_fields = ["titre", "resume", "contenu"]
    autocomplete_fields = ["matiere"]
    prepopulated_fields = {"slug": ("titre",)}
    readonly_fields = ["date_creation", "date_modification"]
    list_select_related = ["matiere"]
    actions = ["publier"]

    @admin.action(description="Publier les cours sélectionnés")
    def publier(self, request, queryset):
        maintenant = timezone.now()
        nombre = queryset.exclude(statut=Cours.Statut.PUBLIE).update(
            statut=Cours.Statut.PUBLIE,
            date_publication=maintenant,
            date_modification=maintenant,
        )
        self.message_user(request, f"{nombre} cours publié(s).", messages.SUCCESS)

Créez un compte administrateur :

uv run python manage.py createsuperuser
uv run python manage.py runserver

Visitez http://127.0.0.1:8000/admin/. Chaque option a un rôle précis :

Option Effet
list_display colonnes affichées dans la liste
list_filter filtres latéraux
search_fields champs interrogés par la barre de recherche
autocomplete_fields champ de sélection avec recherche (exige search_fields sur l’admin de la cible : d’où MatiereAdmin)
prepopulated_fields pré-remplit le slug depuis le titre pendant la saisie
readonly_fields affiche un champ sans permettre de le modifier ; indispensable pour afficher les champs auto_now
list_select_related précharge une relation pour éviter le N+1 dans la liste
actions opérations en masse sur les lignes cochées

Essayez de créer un cours en choisissant le statut « Publié » sans date de publication : l’admin appelle full_clean(), donc la règle de Cours.clean() (chapitre 3) s’applique et affiche l’erreur à côté du champ. Les règles du modèle valent partout.

Une action personnalisée

L’action publier illustre deux conséquences du chapitre 3. D’abord, update() ne met pas à jour auto_now : nous renseignons donc date_modification nous-mêmes. Ensuite, update() ne lance pas clean() : l’action doit donc elle-même respecter la règle « publié ⇒ date de publication », ce qu’elle fait en écrivant les deux champs ensemble. exclude(statut=PUBLIE) évite d’écraser la date d’un cours déjà publié.

L’admin et les performances

Si une liste affiche une relation, Django peut charger chaque matière séparément. list_select_related = ["matiere"] résout cela pour les colonnes de liste. Pour un contrôle total, on peut aussi redéfinir get_queryset :

def get_queryset(self, request):
    return super().get_queryset(request).select_related("matiere")

Mesurez avant d’optimiser, mais ne rendez pas l’admin inutilisable avec une requête N+1 lorsque le catalogue grandit.

Messages utilisateur

Les messages sont temporaires et associés à la prochaine réponse : on les « poste » dans une vue, puis ils s’affichent une seule fois sur la page suivante (typiquement après une redirection).

from django.contrib import messages

messages.success(request, "Le cours a été enregistré.")
messages.error(request, "Impossible de supprimer ce cours.")

Les niveaux disponibles sont debug, info, success, warning et error. Dans base.html, ajoutez le bloc d’affichage juste avant {% block content %} :

  <main class="container">
    {% if messages %}
      <div class="messages" aria-live="polite">
        {% for message in messages %}
          <p class="message message-{{ message.tags }}">{{ message }}</p>
        {% endfor %}
      </div>
    {% endif %}

    {% block content %}{% endblock %}
  </main>

Le contexte est disponible grâce à django.contrib.messages.context_processors.messages, présent dans la configuration initiale. La classe message-{{ message.tags }} (par exemple message-success) permet au CSS de colorer chaque niveau. Un message ne doit pas être la seule façon de communiquer une erreur : le formulaire doit aussi porter les erreurs au niveau du champ.

Erreurs fréquentes

Symptôme Cause probable Remède
Forbidden (403) CSRF verification failed {% csrf_token %} absent du formulaire l’ajouter dans la balise <form method="post">
formulaire invalide, mais aucune erreur affichée le template ne parcourt pas field.errors afficher les erreurs, ou utiliser { form.as_p }
404 juste après la création d’un cours redirection vers la page publique d’un brouillon rediriger vers cours:modifier
ImproperlyConfigured: Creating a ModelForm without either the 'fields' attribute… Meta.fields absent lister explicitement les champs
admin.E039 ou erreur sur autocomplete_fields search_fields absent de l’admin de la cible ajouter search_fields à MatiereAdmin
NoReverseMatch sur cours:modifier route absente ou mal nommée vérifier cours/urls.py
« Ce champ est obligatoire » sur un champ absent du formulaire champ du modèle ni obligatoire ni dans fields donner un default au modèle ou l’ajouter à fields
anonyme redirigé vers une 404 /accounts/login/ page de connexion pas encore créée normal : voir le Authentification, sécurité et fichiers statiques

À retenir

  • La validation importante se fait côté serveur ; les attributs HTML ne protègent rien.
  • Le cycle est liaison → validation → action, suivi d’une redirection (PRG).
  • fields est une liste explicite : un champ absent ne peut pas être modifié par une requête forgée.
  • GET ne modifie jamais l’état ; suppression et modification passent par POST avec jeton CSRF.
  • instance= fait passer un ModelForm de la création à la modification.
  • Une règle métier se place dans le modèle pour valoir partout (formulaire, admin, scripts).
  • update() contourne clean() et auto_now : on les gère soi-même.
  • Les messages sont affichés une fois, après une redirection.
