Où en sommes-nous ?

BiblioCours dispose de routes et de vues qui renvoient du texte. Il n’y a pas encore de données : le contenu est codé en dur dans les vues. Dans ce chapitre, nous décrivons les données (matières et cours), nous créons les tables correspondantes et nous apprenons à les manipuler depuis Python. À la fin, la base contiendra un jeu de données de démonstration dont nous nous servirons aux chapitres 4 et 5.

Penser d’abord au domaine

Avant d’écrire models.py, décrivons les objets du métier. BiblioCours contient des matières et des cours. Une matière regroupe plusieurs cours ; un cours appartient à une seule matière. Cette phrase donne déjà une relation « un-à-plusieurs » :

Matiere  1 ────────< *  Cours
(une matière a plusieurs cours ; un cours a une seule matière)

Un bon modèle répond à des questions concrètes :

  • quelles informations doivent être obligatoires ?
  • quelle taille maximale une valeur peut-elle avoir ?
  • deux enregistrements peuvent-ils porter la même valeur ?
  • que se passe-t-il si la matière d’un cours est supprimée ?
  • quelle date représente la création et quelle date représente la publication ?

Le modèle n’est pas seulement un miroir de la table SQL. Il formalise des règles et fournit une interface Python pour manipuler les données. L’ORM (Object-Relational Mapper) de Django traduit cette interface en requêtes SQL adaptées à la base configurée (Django Software Foundation 2025). La correspondance est systématique :

Côté Python Côté base de données
une classe de modèle (Cours) une table (cours_cours)
un attribut (titre) une colonne
une instance (Cours(...)) une ligne
un QuerySet une requête SELECT

Le nom de la table est formé du nom de l’app et du nom du modèle en minuscules : cours + _ + cours.

Écrire les modèles de BiblioCours

Remplacez le contenu de cours/models.py par :

from django.core.exceptions import ValidationError
from django.db import models
from django.urls import reverse


class Matiere(models.Model):
    nom = models.CharField(max_length=100, unique=True)
    slug = models.SlugField(max_length=110, unique=True)
    description = models.TextField(blank=True)

    class Meta:
        ordering = ["nom"]
        verbose_name = "matière"
        verbose_name_plural = "matières"

    def __str__(self):
        return self.nom


class Cours(models.Model):
    class Statut(models.TextChoices):
        BROUILLON = "brouillon", "Brouillon"
        PUBLIE = "publie", "Publié"

    titre = models.CharField(max_length=200)
    slug = models.SlugField(max_length=220, unique=True)
    resume = models.CharField(max_length=500)
    contenu = models.TextField()
    statut = models.CharField(
        max_length=20,
        choices=Statut.choices,
        default=Statut.BROUILLON,
    )
    matiere = models.ForeignKey(
        Matiere,
        on_delete=models.PROTECT,
        related_name="cours",
    )
    date_creation = models.DateTimeField(auto_now_add=True)
    date_modification = models.DateTimeField(auto_now=True)
    date_publication = models.DateTimeField(null=True, blank=True)

    class Meta:
        ordering = ["-date_creation"]
        verbose_name = "cours"
        verbose_name_plural = "cours"
        indexes = [
            models.Index(fields=["statut", "-date_creation"]),
        ]

    def __str__(self):
        return self.titre

    def clean(self):
        super().clean()
        if self.statut == self.Statut.PUBLIE and self.date_publication is None:
            raise ValidationError(
                {
                    "date_publication": (
                        "Un cours publié doit avoir une date de publication."
                    )
                }
            )

    def get_absolute_url(self):
        return reverse("cours:detail", kwargs={"slug": self.slug})

    @property
    def est_publie(self):
        return self.statut == self.Statut.PUBLIE

Remarquez que nous n’avons déclaré aucune clé primaire : Django ajoute automatiquement une colonne id (un entier auto-incrémenté), que l’on retrouve aussi sous le nom pk (primary key). Le type de cette colonne est défini par DEFAULT_AUTO_FIELD dans settings.py.

Pourquoi ces champs ?

CharField représente une chaîne bornée. max_length est utile pour la base, les formulaires et la documentation de l’intention. TextField convient au contenu dont la taille est plus libre. SlugField représente une valeur adaptée aux URLs, généralement composée de lettres minuscules, chiffres et tirets.

AvertissementTextField(max_length=…) ne protège pas la base

Pour un TextField, max_length est seulement transmis au widget de formulaire : ni le modèle ni la base ne l’imposent. C’est pourquoi le résumé est un CharField(max_length=500) : la limite y est réellement appliquée.

unique=True crée une contrainte d’unicité. Ce n’est pas seulement une validation d’interface : la base elle-même empêchera deux matières d’avoir le même slug. La base est la dernière barrière, car deux requêtes concurrentes peuvent passer simultanément une validation purement applicative.

TextChoices évite les chaînes dispersées dans le code. La valeur enregistrée est "publie" et le libellé affiché est "Publié". On peut écrire Cours.Statut.PUBLIE dans le code et laisser Django gérer les choix.

auto_now_add est évalué à la création ; auto_now à chaque sauvegarde.

La différence entre null et blank revient souvent et prête à confusion :

Option Concerne Effet
null=True la base la colonne accepte la valeur NULL
blank=True la validation (formulaires, admin) le champ peut rester vide
default=… la création valeur utilisée si rien n’est fourni

blank=True ne rend donc pas automatiquement une colonne SQL nullable. Ici, date_publication est null=True, blank=True : un brouillon n’a pas de date de publication. En revanche, pour un champ texte comme description, on met seulement blank=True : la valeur « vide » est la chaîne "", et non NULL (avoir deux façons de dire « vide » compliquerait les requêtes).

La classe Meta regroupe les options du modèle : ordering définit l’ordre par défaut des résultats, verbose_name les noms affichés dans l’administration (sans verbose_name_plural = "cours", Django afficherait « courss »), et indexes un index de base de données qui accélère les requêtes filtrant sur statut et triant sur la date. La méthode __str__ donne la représentation textuelle d’un objet, utilisée dans l’administration et le shell. get_absolute_url centralise l’adresse d’un objet : templates et redirections n’auront jamais à reconstruire l’URL. Enfin est_publie est une propriété Python : elle se calcule à partir de statut et n’est pas une colonne.

Choisir on_delete

La relation vers Matiere utilise PROTECT. Supprimer une matière qui possède encore des cours serait probablement une erreur métier ; Django lève donc une exception plutôt que d’effacer silencieusement le catalogue.

Les comportements courants sont :

  • CASCADE : supprimer les objets liés ;
  • PROTECT : refuser la suppression ;
  • SET_NULL : mettre la relation à NULL si null=True ;
  • SET_DEFAULT : utiliser la valeur par défaut ;
  • DO_NOTHING : ne rien orchestrer, choix réservé aux cas maîtrisés.

Il n’existe pas de choix universel. Pour une photo liée à un profil, CASCADE peut être logique. Pour une facture liée à un client, PROTECT est souvent plus sûr. Posez-vous la question : si le parent disparaît, l’enfant a-t-il encore un sens ?

L’argument related_name="cours" nomme la relation inverse : à partir d’une matière, matiere.cours donne tous ses cours.

Valider au niveau du modèle

Notre méthode clean() exprime une règle métier : un cours publié doit avoir une date de publication. Cette règle appartient au modèle, car elle doit rester vraie quel que soit le chemin de création : formulaire public, administration ou script.

Mais attention : save() n’appelle pas clean(). Seul full_clean() lance toutes les validations (champs, clean(), unicité), et ce sont les ModelForm et l’administration qui l’appellent pour vous (chapitre 5). Dans le shell, un Cours.objects.create(...) écrit en base sans rien vérifier de ce qui n’est pas une contrainte SQL. Nous le constaterons plus bas.

Les migrations : l’historique du schéma

Un modèle Python et une table SQL ne sont pas la même chose. La migration est le fichier qui décrit une transformation du schéma. Le flux est toujours le même :

modèle modifié ──makemigrations──▶ fichier de migration ──migrate──▶ base mise à jour
uv run python manage.py makemigrations cours
uv run python manage.py migrate

makemigrations compare l’état actuel des modèles avec l’historique des migrations et génère un fichier Python dans cours/migrations/. migrate exécute les migrations non appliquées dans la base. Cette seconde commande crée le fichier db.sqlite3 s’il n’existe pas et applique aussi les migrations des composants Django (authentification, administration, sessions) : l’avertissement rencontré au chapitre 1 disparaît.

Ouvrez cours/migrations/0001_initial.py. Vous y lirez, en version abrégée :

class Migration(migrations.Migration):
    initial = True

    dependencies = []

    operations = [
        migrations.CreateModel(
            name="Matiere",
            fields=[
                ("id", models.BigAutoField(primary_key=True, ...)),
                ("nom", models.CharField(max_length=100, unique=True)),
                # ...
            ],
        ),
        migrations.CreateModel(name="Cours", fields=[...]),
    ]

Une migration est du code : relisez-la avant de l’appliquer. Inspectez aussi ce que Django prévoit :

uv run python manage.py showmigrations
uv run python manage.py sqlmigrate cours 0001

showmigrations liste les migrations et indique par [X] celles qui sont appliquées. sqlmigrate montre le SQL généré sans l’exécuter :

BEGIN;
CREATE TABLE "cours_matiere" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    "nom" varchar(100) NOT NULL UNIQUE,
    ...
);

C’est un excellent outil pour relier le code Python à la réalité de la base.

Faire évoluer un modèle

Quand vous modifiez un modèle (ajout d’un champ, par exemple), relancez makemigrations : Django produit une nouvelle migration (0002_…). Si le champ est obligatoire et que des lignes existent déjà, Django demande quelle valeur donner aux lignes existantes : fournissez un default plutôt que de laisser une colonne NOT NULL sans valeur.

AvertissementNe modifiez pas une migration déjà partagée

Une migration appliquée fait partie de l’histoire du schéma. En équipe, créez une nouvelle migration plutôt que de réécrire une ancienne. Modifier une migration déjà exécutée peut créer des divergences entre les bases des collaborateurs et la base de production.

Tant qu’une migration n’a jamais quitté votre machine (pas de commit partagé), vous pouvez la supprimer, effacer db.sqlite3 et la régénérer : c’est une façon propre de corriger un modèle en cours d’apprentissage.

Les fichiers de migration doivent être versionnés. La base SQLite locale ne l’est généralement pas, mais les instructions permettant de la recréer le sont.

Lire et naviguer dans les relations

python_cours.matiere        # <Matiere: Informatique>
informatique.cours.all()    # tous les cours de la matière
Cours.objects.filter(statut=Cours.Statut.PUBLIE)

Chaque accès à .objects construit ou exécute un QuerySet. Un QuerySet est évalué de manière différée : écrire cours = Cours.objects.filter(...) ne signifie pas nécessairement qu’une requête SQL est déjà partie. L’évaluation arrive lors d’une itération, d’une conversion en liste, d’un len, ou de l’accès à certains résultats. Vous pouvez voir le SQL qui sera exécuté :

qs = Cours.objects.filter(statut=Cours.Statut.PUBLIE)  # aucune requête SQL
print(qs.query)                                         # affiche le SQL
len(qs)                                                 # c'est ici qu'elle part

Cette paresse permet de chaîner les opérations (filter, exclude, order_by…) pour construire une seule requête optimisée.

Filtrer, trier et limiter

Cours.objects.filter(titre__icontains="python")
Cours.objects.filter(matiere__slug="informatique")
Cours.objects.filter(
    statut=Cours.Statut.PUBLIE,
    matiere__nom__iexact="informatique",
)
Cours.objects.exclude(statut=Cours.Statut.BROUILLON)
Cours.objects.order_by("-date_publication")[:10]

Les doubles underscores traversent des relations et expriment des recherches. Les plus utiles :

Suffixe Signification Exemple
__exact (défaut) égalité statut="publie"
__iexact égalité sans casse nom__iexact="python"
__contains / __icontains contient (sans casse pour i) titre__icontains="py"
__startswith commence par titre__startswith="Intro"
__in appartient à une liste statut__in=["publie"]
__gt, __gte, __lt, __lte comparaisons date_publication__gte=…
__isnull est (ou non) nul date_publication__isnull=True

Le tri "-date_publication" (avec un tiret) est décroissant ; [:10] limite à dix résultats (c’est un LIMIT SQL, pas un découpage en mémoire).

filter renvoie un QuerySet (éventuellement vide), tandis que get attend exactement un résultat :

cours = Cours.objects.get(slug="python-pour-debutants")

Si aucun objet ne correspond, get lève Cours.DoesNotExist ; si plusieurs correspondent, il lève Cours.MultipleObjectsReturned. Pour une vue, get_object_or_404 transforme l’absence en réponse HTTP 404, plutôt que de laisser remonter une exception non gérée. D’autres méthodes pratiques : count(), exists(), first().

select_related et prefetch_related

Afficher une liste de cours et le nom de leur matière peut provoquer une requête par cours si l’on ne prépare pas la relation. C’est le problème classique du N+1 : une requête pour la liste, puis une de plus pour chacun des N éléments. Mesurons-le :

from django.db import connection
from django.test.utils import CaptureQueriesContext

with CaptureQueriesContext(connection) as sans:
    for cours in Cours.objects.all():
        cours.matiere.nom

with CaptureQueriesContext(connection) as avec:
    for cours in Cours.objects.select_related("matiere"):
        cours.matiere.nom

print(len(sans), len(avec))   # par exemple : 28 1

La version naïve exécute une requête par cours ; avec select_related, une seule jointure suffit. select_related utilise une jointure SQL pour les relations à valeur unique comme ForeignKey. Pour une relation inverse ou plusieurs-à-plusieurs, utilisez prefetch_related, qui exécute une requête supplémentaire pour toutes les relations et assemble les résultats en Python :

matieres = Matiere.objects.prefetch_related("cours").all()

Il ne faut pas ajouter ces méthodes mécaniquement. Mesurez les requêtes et choisissez l’outil adapté à la relation et à l’écran.

Modifier les données avec prudence

Ces deux formes ne sont pas équivalentes :

cours = Cours.objects.get(pk=1)
cours.titre = "Nouveau titre"
cours.save(update_fields=["titre", "date_modification"])

et :

Cours.objects.filter(pk=1).update(titre="Nouveau titre")
save() sur une instance update() sur un QuerySet
exécute un UPDATE pour cet objet un UPDATE pour toutes les lignes visées
appelle un save() personnalisé oui non
met à jour auto_now oui non (à fournir soi-même)
lance clean() non non

save passe par le cycle de sauvegarde de l’instance (d’où update_fields=[..., "date_modification"] : on demande explicitement de mettre à jour la date). update exécute une mise à jour SQL directe. Pour une opération en masse, update est efficace, mais il faut connaître ses conséquences : notamment qu’il laisse date_modification inchangé.

Pour une opération composée de plusieurs écritures, utilisez une transaction :

from django.db import transaction
from django.utils import timezone


@transaction.atomic
def publier(cours):
    cours.statut = Cours.Statut.PUBLIE
    cours.date_publication = timezone.now()
    cours.save(
        update_fields=["statut", "date_publication", "date_modification"]
    )

Si une exception survient dans le bloc atomique, Django annule les opérations de la transaction : soit toutes les écritures réussissent, soit aucune. La transaction protège la cohérence des données ; elle ne remplace pas la validation métier.

Concevoir avant de migrer

Ajoutez les champs uniquement lorsqu’ils correspondent à un besoin. Un champ description et un champ contenu ne sont pas interchangeables si leurs contraintes et leurs usages diffèrent. À l’inverse, ne créez pas un champ est_publie en plus de statut : deux sources de vérité peuvent diverger. C’est pourquoi est_publie est une propriété calculée, et non une colonne.

Le bon flux est :

  1. décrire la règle métier ;
  2. choisir le type et les contraintes ;
  3. modifier le modèle ;
  4. lire la migration générée ;
  5. appliquer et tester la migration ;
  6. essayer les cas normaux et les cas limites.

Checkpoint

Erreurs fréquentes

Symptôme Cause probable Remède
OperationalError: no such table: cours_cours migrate oublié lancer migrate
IntegrityError: UNIQUE constraint failed slug ou nom déjà utilisé choisir une autre valeur
IntegrityError: NOT NULL constraint failed champ obligatoire non renseigné fournir une valeur ou un default
ProtectedError suppression d’une matière qui a des cours supprimer/déplacer d’abord les cours
Cours.DoesNotExist get sans résultat utiliser filter ou get_object_or_404
Your models have changes that are not yet reflected… makemigrations oublié le lancer, puis migrate
create accepte des données invalides create ne valide pas appeler full_clean() ou passer par un formulaire

À retenir

  • Le modèle décrit des règles, pas seulement des colonnes ; la base est la dernière barrière.
  • null concerne la base, blank la validation.
  • Choisissez on_delete en vous demandant si l’enfant a un sens sans le parent.
  • Une migration est un fichier de code qui raconte l’histoire du schéma ; on la relit et on la versionne.
  • Un QuerySet est paresseux ; mesurez les requêtes pour repérer le N+1.
  • save() et update() n’ont pas les mêmes effets ; save() ne valide pas.
  • Une règle métier ne doit avoir qu’une seule source de vérité.
