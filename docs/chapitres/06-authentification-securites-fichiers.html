Où en sommes-nous ?

Les vues de création, de modification et de suppression existent (chapitre 5), mais elles sont protégées uniquement par login_required, et le site n’a pas de page de connexion : il faut passer par l’administration. Surtout, tout utilisateur connecté peut tout faire. Ce chapitre installe un vrai contrôle d’accès, puis range la configuration sensible là où elle doit être.

Authentifier n’est pas autoriser

Deux questions différentes sont souvent confondues :

  • authentification : « qui est cette personne ? » ;
  • autorisation : « a-t-elle le droit de faire cette action ? ».

Un utilisateur connecté peut avoir le droit de lire un cours mais pas de le supprimer. La présence de request.user ne suffit donc jamais à autoriser une opération.

Django fournit un système d’utilisateurs, de sessions, de groupes et de permissions. Il faut le configurer et l’utiliser de manière explicite plutôt que d’inventer un mécanisme de mot de passe. Les recommandations de sécurité du framework et les contrôles OWASP complètent cette compréhension (Django Software Foundation 2025b; OWASP Foundation 2021).

Comment fonctionne une session

HTTP est « sans mémoire » : chaque requête est indépendante, et le serveur ne sait pas, de lui-même, que deux requêtes viennent de la même personne. Django résout cela avec une session :

1. POST /connexion/  (identifiant + mot de passe)
2. Django vérifie le mot de passe, crée une session (une ligne dans la table
   django_session) et répond :  Set-Cookie: sessionid=abc123…
3. GET /cours/nouveau/   +  Cookie: sessionid=abc123…   (automatique, à chaque requête)
4. SessionMiddleware retrouve la session ; AuthenticationMiddleware place
   l'utilisateur dans request.user

Le navigateur ne conserve donc qu’un identifiant de session dans un cookie ; les données restent côté serveur. Les mots de passe ne sont jamais stockés en clair : Django ne conserve qu’une empreinte (un hash salé), d’où l’importance de créer les comptes avec create_user ou l’administration, et non en écrivant dans la base à la main.

Ajouter les routes d’authentification

Dans config/urls.py :

from django.contrib import admin
from django.contrib.auth import views as auth_views
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("cours/", include("cours.urls")),
    path(
        "connexion/",
        auth_views.LoginView.as_view(template_name="registration/login.html"),
        name="login",
    ),
    path("deconnexion/", auth_views.LogoutView.as_view(), name="logout"),
]

LoginView et LogoutView sont des vues fournies par Django : elles traitent le formulaire, vérifient le mot de passe et gèrent la session. Nous n’avons qu’à fournir le template. Ajoutez dans config/settings.py :

LOGIN_URL = "login"
LOGIN_REDIRECT_URL = "cours:liste"
LOGOUT_REDIRECT_URL = "cours:liste"

LOGIN_URL est la page vers laquelle login_required redirige les anonymes ; LOGIN_REDIRECT_URL la destination après une connexion réussie (sauf si un paramètre next existe) ; LOGOUT_REDIRECT_URL la destination après la déconnexion. Ces trois valeurs peuvent être des noms de routes.

Le template de connexion doit se trouver à l’emplacement attendu :

templates/
└── registration/
    └── login.html

Ce dossier templates/ est à la racine du projet et non dans l’app : c’est un template qui concerne le site entier. Pour qu’il soit trouvé, déclarez-le dans le réglage TEMPLATES existant :

TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [BASE_DIR / "templates"],
        "APP_DIRS": True,
        # ... le reste inchangé
    },
]

DIRS liste les dossiers « globaux » où chercher des templates ; APP_DIRS les dossiers templates/ de chaque app. templates/registration/login.html :

{% extends "cours/base.html" %}

{% block title %}Connexion — BiblioCours{% endblock %}

{% block content %}
  <h1>Se connecter</h1>
  <form method="post">
    {% csrf_token %}
    {{ form.as_p }}
    <button type="submit">Se connecter</button>
  </form>
{% endblock %}

Ce formulaire n’a pas d’attribut action : il est donc envoyé à l’URL courante, paramètres compris. Quand un anonyme est redirigé vers /connexion/?next=/cours/nouveau/, ce paramètre next accompagne le POST et LoginView renvoie l’utilisateur vers la page qu’il voulait atteindre. Django vérifie que next pointe vers un hôte autorisé (voir « Redirections » plus bas).

Dans base.html, adaptez la navigation (remplacez le bloc <nav>) :

<nav aria-label="Navigation principale">
  <a href="{% url 'cours:liste' %}">BiblioCours</a>
  <a href="{% url 'cours:a_propos' %}">À propos</a>
  {% if perms.cours.add_cours %}
    <a href="{% url 'cours:creer' %}">Nouveau cours</a>
  {% endif %}
  {% if user.is_authenticated %}
    <span>Bonjour {{ user.get_username }}</span>
    <form method="post" action="{% url 'logout' %}" class="inline-form">
      {% csrf_token %}
      <button type="submit">Se déconnecter</button>
    </form>
  {% else %}
    <a href="{% url 'login' %}?next={{ request.path|urlencode }}">
      Se connecter
    </a>
  {% endif %}
</nav>

Les variables user et perms viennent du context processor django.contrib.auth.context_processors.auth : elles sont disponibles dans tous les templates. Sur les versions récentes de Django, la déconnexion est traitée par POST. Utiliser un formulaire respecte le fait que la déconnexion modifie l’état de la session ; un simple lien déclencherait une erreur 405 Method Not Allowed.

Protéger une vue et une action

Le décorateur protège la présence d’une session :

from django.contrib.auth.decorators import login_required


@login_required
def creer_cours(request):
    ...

Pour une permission :

from django.contrib.auth.decorators import login_required, permission_required


@login_required
@permission_required("cours.add_cours", raise_exception=True)
def creer_cours(request):
    ...

Chaque modèle reçoit automatiquement quatre permissions : add, change, delete et view. Leur nom suit le modèle app.action_modele, par exemple cours.add_cours.

Remarquez l’empilement des décorateurs, dans cet ordre. Il fournit trois comportements distincts :

Qui appelle la vue ? Résultat
un visiteur anonyme redirection vers la connexion (login_required)
un utilisateur connecté sans la permission 403 Forbidden (raise_exception=True)
un utilisateur connecté avec la permission la vue s’exécute

raise_exception=True renvoie une réponse interdite (403) au lieu de rediriger silencieusement. Sans login_required au-dessus, un anonyme recevrait aussi un 403 plutôt qu’une invitation à se connecter. Choisissez le comportement en fonction du contexte : une app publique peut vouloir masquer l’existence d’une ressource ; une interface interne doit souvent expliquer le manque de permission.

Voici la protection finale des trois vues du chapitre 5 (seul l’en-tête change, le corps reste identique) :

@login_required
@permission_required("cours.add_cours", raise_exception=True)
def creer_cours(request): ...


@login_required
@permission_required("cours.change_cours", raise_exception=True)
def modifier_cours(request, slug): ...


@login_required
@permission_required("cours.delete_cours", raise_exception=True)
def supprimer_cours(request, slug): ...

Un groupe « Éditeurs »

Plutôt que d’attribuer des permissions utilisateur par utilisateur, on les regroupe. Dans l’administration :

  1. Groupes → Ajouter : nommez le groupe Éditeurs ;
  2. choisissez les permissions cours | cours | Can add cours, Can change cours et Can view cours (pas Can delete cours) ;
  3. Utilisateurs → Ajouter : créez un compte « edith » avec un mot de passe, puis, dans sa fiche, ajoutez-la au groupe Éditeurs.

Ce compte n’a pas besoin de la case « Statut équipe » (is_staff) pour utiliser le site : cette case ne sert qu’à accéder à l’administration. Les permissions add et change suffisent pour créer et modifier des cours via le site ; seule la suppression leur est refusée. Seuls les comptes is_staff ayant la permission change_cours peuvent publier dans l’admin.

AstuceMasquer n’est pas protéger

Le lien « Nouveau cours » n’apparaît que pour qui possède la permission ({% if perms.cours.add_cours %}) : c’est de l’ergonomie. La sécurité, elle, est dans le décorateur de la vue : un utilisateur qui connaît l’URL /cours/nouveau/ mais n’a pas la permission reçoit un 403. Faites toujours les deux, et ne comptez jamais sur le masquage seul.

Dans detail.html, vous pouvez de la même façon n’afficher un lien « Modifier » qu’aux personnes autorisées :

{% if perms.cours.change_cours %}
  <p><a href="{% url 'cours:modifier' cours.slug %}">Modifier ce cours</a></p>
{% endif %}
NoteLimite : permissions globales et par objet

Les permissions de Django portent sur un modèle entier : qui possède change_cours peut modifier tous les cours. Autoriser seulement l’auteur d’un cours à le modifier demande une règle supplémentaire par objet (par exemple comparer cours.auteur à request.user), ce que l’exercice 12 explore.

CSRF : protéger les requêtes qui changent l’état

Une attaque CSRF (Cross-Site Request Forgery) amène le navigateur d’une victime déjà connectée à envoyer une requête vers un site où elle est authentifiée. Exemple : une page piégée contient un formulaire invisible qui envoie un POST vers /cours/mon-cours/supprimer/. Le navigateur peut joindre les cookies automatiquement, donc la requête arrive avec la session de la victime ; le serveur doit donc exiger un jeton que le site attaquant ne peut pas lire.

Dans un formulaire interne :

<form method="post">
  {% csrf_token %}
  …
</form>

CsrfViewMiddleware compare le jeton du formulaire à celui du cookie et refuse le POST (403) en cas de différence. Pour un appel JavaScript, le jeton doit être envoyé dans l’en-tête X-CSRFToken, selon la configuration Django. Ne désactivez pas CsrfViewMiddleware (ni @csrf_exempt) pour contourner une erreur : cherchez plutôt pourquoi le cookie ou le jeton ne correspond pas (Django Software Foundation 2025a).

Échappement, injection et entrées utilisateur

Une règle domine ce chapitre : toute donnée venant de l’extérieur est hostile jusqu’à preuve du contraire — paramètres d’URL, formulaires, en-têtes, fichiers, et même contenu saisi en administration.

XSS et templates

Une attaque XSS (Cross-Site Scripting) injecte du JavaScript dans une page vue par d’autres utilisateurs. Django échappe les variables dans les templates par défaut :

{{ commentaire.texte }}

Si un utilisateur enregistre <img src=x onerror=alert(1)>, cette valeur doit rester du texte : Django envoie &lt;img src=x …&gt;, que le navigateur affiche tel quel au lieu de l’exécuter. Le filtre safe supprime la protection :

{{ contenu_html|safe }}

Ne l’utilisez que si le contenu a été nettoyé par une bibliothèque adaptée à votre format et à votre modèle de menace. Le fait qu’une donnée vienne de l’admin ne garantit pas que tous les administrateurs soient dignes de confiance ni que le champ soit toujours contrôlé.

Injection SQL

Une injection SQL glisse du SQL dans une requête construite par concaténation : avec f"… WHERE titre = '{terme}'", un terme comme ' OR 1=1 -- change le sens de la requête. L’ORM paramètre les valeurs, c’est-à-dire qu’il les transmet séparément de la requête :

Cours.objects.filter(titre__icontains=terme)

Évitez de construire du SQL avec une f-string. Si une requête SQL brute est nécessaire, utilisez des paramètres et expliquez la raison dans le code :

Cours.objects.raw(
    "SELECT * FROM cours_cours WHERE titre LIKE %s",
    [f"%{terme}%"],
)

Le nom de la table, cours_cours, suit la règle vue au chapitre 3. Le SQL brut n’est pas « plus professionnel ». Il augmente la responsabilité du développeur concernant les paramètres, les noms de tables, les performances et la portabilité.

Redirections

Une redirection ouverte permet à un attaquant de fabriquer un lien légitime (votre-site.fr/…?next=https://site-pirate.example) qui renvoie vers un site malveillant. Ne redirigez pas aveuglément vers une URL fournie par l’utilisateur. Un paramètre next doit être validé comme une destination sûre :

from django.shortcuts import redirect
from django.utils.http import url_has_allowed_host_and_scheme


def apres_action(request):
    suivant = request.POST.get("next", "")
    if url_has_allowed_host_and_scheme(
        suivant,
        allowed_hosts={request.get_host()},
        require_https=request.is_secure(),
    ):
        return redirect(suivant)
    return redirect("cours:liste")

LoginView applique déjà ce contrôle à son paramètre next.

Risque Protection fournie Votre responsabilité

injection SQL paramétrage par l’ORM ne pas concaténer de SQL

Secrets et configuration

Jusqu’ici, SECRET_KEY, DEBUG et ALLOWED_HOSTS sont écrits en dur dans settings.py, donc dans Git. C’est dangereux : toute personne qui lit le dépôt connaît la clé qui signe vos sessions. La règle est de séparer la configuration du code : le code est identique partout, et chaque environnement (poste de développement, serveur) fournit ses propres valeurs par des variables d’environnement.

Modifiez le début de config/settings.py :

import os
from pathlib import Path

from django.core.exceptions import ImproperlyConfigured

BASE_DIR = Path(__file__).resolve().parent.parent


def env_requis(nom):
    """Lit une variable d'environnement obligatoire."""
    valeur = os.environ.get(nom)
    if not valeur:
        raise ImproperlyConfigured(
            f"La variable d'environnement {nom} est requise "
            "(voir le fichier .env.example)."
        )
    return valeur


def env_liste(nom):
    """Lit une liste de valeurs séparées par des virgules."""
    brut = os.environ.get(nom, "")
    return [valeur.strip() for valeur in brut.split(",") if valeur.strip()]


SECRET_KEY = env_requis("DJANGO_SECRET_KEY")
DEBUG = os.environ.get("DJANGO_DEBUG", "false").lower() == "true"
ALLOWED_HOSTS = env_liste("DJANGO_ALLOWED_HOSTS")

Deux choix méritent d’être expliqués :

  • DEBUG vaut False par défaut : si la variable est oubliée en production, le site reste sûr (on dit qu’il « échoue en sécurité »). Le mode debug doit être demandé explicitement ;
  • l’absence de DJANGO_SECRET_KEY provoque une erreur lisible (ImproperlyConfigured) plutôt qu’un KeyError obscur, et empêche de démarrer avec une clé par défaut.

Fournir les valeurs en local

Créez à la racine un fichier .env (déjà ignoré par Git depuis le chapitre 1) :

DJANGO_SECRET_KEY=une-cle-locale-longue-et-aleatoire
DJANGO_DEBUG=true
DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost

Pour fabriquer une clé aléatoire :

uv run python -c "import secrets; print(secrets.token_urlsafe(50))"

Créez aussi un fichier .env.example sans secret, qui, lui, est versionné : il documente les variables attendues.

DJANGO_SECRET_KEY=remplacez-moi
DJANGO_DEBUG=true
DJANGO_ALLOWED_HOSTS=127.0.0.1,localhost
ImportantChangement de routine : charger .env

uv run peut charger le fichier .env pour vous. La méthode la plus simple est de le préciser pour chaque commande :

uv run --env-file .env python manage.py runserver
uv run --env-file .env python manage.py test

Pour éviter de répéter l’option, vous pouvez définir UV_ENV_FILE pour la session du terminal. Sous macOS/Linux :

export UV_ENV_FILE=.env

Sous PowerShell :

$env:UV_ENV_FILE = ".env"

Dans ce terminal, les commandes uv run python manage.py runserver, test et check chargeront le même fichier. Si une nouvelle fenêtre de terminal est ouverte, il faut y redéfinir la variable, ou utiliser --env-file .env. Si Django signale que DJANGO_SECRET_KEY manque, vérifiez que .env se trouve à la racine du projet et que la commande charge bien ce fichier. Ne remplacez pas cette erreur par une clé secrète par défaut.

Ne commitez ni clé secrète, ni mot de passe de base, ni token de service. Un fichier .env peut aider en local mais doit être ignoré par Git et ne doit pas être copié dans une archive de déploiement. En production, utilisez le système de secrets de l’hébergeur (voir Préparer la production et continuer l’apprentissage).

Fichiers statiques

Les fichiers statiques sont le CSS, le JavaScript et les images livrés avec le code : ils ne changent pas d’une requête à l’autre. Django les trouve grâce à des finders (chercheurs) qui explorent deux types d’emplacements :

Emplacement Réglage Exemple
dossier static/ d’une app automatique (AppDirectoriesFinder) cours/static/cours/site.css
dossiers du projet STATICFILES_DIRS static/ à la racine

Notre feuille cours/static/cours/site.css (créée au chapitre 4) est donc déjà trouvée sans réglage. Configurez la partie nécessaire au déploiement dans config/settings.py :

STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"

Et, si vous voulez des fichiers statiques propres au projet (hors app), ajoutez :

STATICFILES_DIRS = [BASE_DIR / "static"]

(le dossier static/ doit alors exister, sinon check émet un avertissement).

Le template les charge avec {% load static %} et {% static 'cours/site.css' %}. En développement, runserver les sert si DEBUG=True. En production, la commande suivante rassemble les fichiers de tous les emplacements :

uv run python manage.py collectstatic

STATIC_ROOT est un dossier de sortie ; il ne doit pas être confondu avec STATICFILES_DIRS, qui contient les sources. Un serveur web ou un stockage objet servira ensuite le contenu rassemblé. Pour diagnostiquer, findstatic indique où Django trouve un fichier :

uv run python manage.py findstatic cours/site.css

Téléversements et fichiers média

Un fichier envoyé par un utilisateur n’est pas un fichier statique : il n’existe pas au moment du déploiement et n’est pas de confiance. Configurez :

MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"

MEDIA_ROOT est le dossier où Django écrit les fichiers envoyés ; MEDIA_URL le préfixe sous lequel on les sert. Voici l’idée, à titre d’illustration (nous ne modifions pas le modèle Cours pour l’instant : voir l’exercice 11) :

document = models.FileField(upload_to="cours/%Y/%m", blank=True)

upload_to indique le sous-dossier de destination, ici organisé par année et mois. Un formulaire qui accepte des fichiers doit déclarer enctype="multipart/form-data" et la vue lire request.FILES en plus de request.POST. En développement seulement, on peut servir les médias depuis config/urls.py :

from django.conf import settings
from django.conf.urls.static import static

if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)

Un upload doit être limité par taille et type, renommé par Django et stocké avec des permissions correctes. Ne vous fiez ni au nom du fichier ni au type déclaré par le navigateur : ils sont fournis par l’utilisateur. Ne servez pas aveuglément un fichier comme du HTML actif. Pour des données sensibles ou volumineuses, un stockage séparé avec des URLs temporaires est souvent plus adapté.

Checklist de sécurité locale

Avant de publier :

  • DEBUG=False ;
  • SECRET_KEY fourni par l’environnement ;
  • ALLOWED_HOSTS renseigné ;
  • HTTPS activé et cookies sécurisés configurés ;
  • protection CSRF conservée ;
  • permissions testées avec un utilisateur normal ;
  • pas de secret dans Git ;
  • uploads limités et traités comme non fiables ;
  • python manage.py check --deploy exécuté.

La sécurité n’est pas une étape à la fin. Chaque champ, route et action doit répondre à la question : qui peut faire quoi, avec quelles données, et que se passe-t-il si la requête est fabriquée à la main ?

À retenir

  • Authentifier = qui ? Autoriser = a-t-il le droit ? Les deux sont nécessaires et distincts.
  • Une session est un cookie contenant un identifiant ; les données sont côté serveur.
  • login_required + permission_required(raise_exception=True) donnent : redirection pour l’anonyme, 403 pour l’utilisateur sans droit.
  • Masquer un lien est de l’ergonomie ; le contrôle dans la vue est la sécurité.
  • Toute entrée est hostile : échappement des templates, ORM paramétré, redirections validées, jeton CSRF.
  • Les secrets viennent de l’environnement, jamais du dépôt ; DEBUG est faux par défaut.
  • Fichiers statiques (code, collectstatic) et média (utilisateurs, non fiables) sont deux choses différentes.
