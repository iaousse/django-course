Un test décrit un contrat

Un test utile ne vérifie pas que l’implémentation ressemble à ce que le développeur avait en tête. Il vérifie un comportement observable :

lorsqu’un visiteur demande la liste, la réponse est 200 et ne montre que les cours publiés.

Cette formulation résiste mieux aux refactorings que « la vue appelle telle fonction ». Les tests de Django peuvent utiliser une base de données de test, un client HTTP de test et les outils reverse et assertContains (Django Software Foundation 2025). Cette manière de partir du comportement attendu rejoint l’approche de développement piloté par les tests décrite par Percival et Gregory (Percival et Gregory 2024).

Lancer la suite

Django fournit une commande intégrée :

uv run python manage.py test

Elle découvre les classes SimpleTestCase, TestCase et les fonctions de test dans les modules dont le nom commence généralement par test. La base de test est créée temporairement et détruite à la fin.

Ajoutez un dossier dédié :

cours/
└── tests/
    ├── __init__.py
    ├── test_models.py
    ├── test_views.py
    └── test_forms.py

Tester le modèle

cours/tests/test_models.py :

from django.test import TestCase

from cours.models import Cours, Matiere


class CoursModelTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.matiere = Matiere.objects.create(
            nom="Informatique",
            slug="informatique",
        )

    def test_str_retourne_le_titre(self):
        cours = Cours(
            titre="Python",
            slug="python",
            resume="Un résumé suffisamment long.",
            contenu="Du contenu.",
            matiere=self.matiere,
        )
        self.assertEqual(str(cours), "Python")

    def test_url_absolue_utilise_le_slug(self):
        cours = Cours.objects.create(
            titre="Python",
            slug="python",
            resume="Un résumé suffisamment long.",
            contenu="Du contenu.",
            matiere=self.matiere,
        )
        self.assertEqual(cours.get_absolute_url(), "/cours/python/")

setUpTestData crée les données une fois pour la classe, ce qui est souvent plus rapide que setUp, exécuté avant chaque méthode. Utilisez setUp si le test doit modifier son jeu de données sans contaminer les autres tests.

Le test ne suppose pas que la table cours_cours existait déjà : Django applique les migrations à la base isolée. C’est une raison de tester les migrations sur une base vide plutôt que de compter sur votre SQLite locale.

Tester les URLs et les vues

cours/tests/test_views.py :

from django.test import TestCase
from django.urls import reverse

from cours.models import Cours, Matiere


class ListeCoursTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        matiere = Matiere.objects.create(
            nom="Informatique",
            slug="informatique",
        )
        Cours.objects.create(
            titre="Cours visible",
            slug="visible",
            resume="Résumé visible.",
            contenu="Contenu visible.",
            matiere=matiere,
            statut=Cours.Statut.PUBLIE,
        )
        Cours.objects.create(
            titre="Cours caché",
            slug="cache",
            resume="Résumé interne.",
            contenu="Brouillon.",
            matiere=matiere,
            statut=Cours.Statut.BROUILLON,
        )

    def test_liste_repond_200(self):
        response = self.client.get(reverse("cours:liste"))

        self.assertEqual(response.status_code, 200)
        self.assertTemplateUsed(response, "cours/liste.html")
        self.assertContains(response, "Cours visible")
        self.assertNotContains(response, "Cours caché")

    def test_detail_inconnu_renvoie_404(self):
        response = self.client.get(
            reverse("cours:detail", kwargs={"slug": "inexistant"})
        )

        self.assertEqual(response.status_code, 404)

self.client simule un navigateur sans lancer de serveur. reverse fait apparaître les erreurs de nom de route immédiatement. assertNotContains est important ici : un filtre qui afficherait aussi les brouillons serait une régression fonctionnelle et potentiellement une fuite d’information.

Tester l’authentification et les permissions

from django.contrib.auth import get_user_model

User = get_user_model()


class CreationCoursTests(TestCase):
    def setUp(self):
        self.user = User.objects.create_user(
            username="alice",
            password="mot-de-passe-de-test",
        )

    def test_visiteur_redirige_vers_connexion(self):
        response = self.client.get(reverse("cours:creer"))

        self.assertEqual(response.status_code, 302)
        self.assertIn("/connexion/", response.url)

    def test_utilisateur_connecte_peut_afficher_le_formulaire(self):
        self.client.force_login(self.user)

        response = self.client.get(reverse("cours:creer"))

        self.assertEqual(response.status_code, 200)
        self.assertContains(response, "Créer un cours")

force_login évite de tester le formulaire de connexion en même temps que la vue de création. Un test doit isoler le comportement qu’il décrit.

Tester un formulaire

from django.test import TestCase

from cours.forms import CoursForm
from cours.models import Matiere


class CoursFormTests(TestCase):
    def setUp(self):
        self.matiere = Matiere.objects.create(
            nom="Python",
            slug="python",
        )

    def test_titre_trop_court_invalide_le_formulaire(self):
        form = CoursForm(
            data={
                "titre": "Py",
                "slug": "py",
                "resume": "Un résumé.",
                "contenu": "Contenu.",
                "matiere": self.matiere.pk,
            }
        )

        self.assertFalse(form.is_valid())
        self.assertIn("titre", form.errors)

Le test appelle is_valid() avant de consulter errors. Les valeurs de ForeignKey transmises à un formulaire HTTP sont des identifiants, pas des instances Python.

Déboguer sans deviner

Quand un test échoue, lisez le premier échec et son traceback. Puis répondez aux questions suivantes :

  1. l’échec est-il dans l’arrangement des données, l’action, ou l’assertion ?
  2. l’exception appartient-elle au code de production ou au test ?
  3. le comportement attendu a-t-il changé volontairement ?
  4. un autre test échoue-t-il à cause d’un état partagé ?

Les tests Django isolent la base, mais pas forcément les variables globales ou les fichiers que votre code écrit sur disque. Évitez les effets de bord et utilisez des répertoires temporaires pour les tests de fichiers.

Pour observer les requêtes exécutées dans un test :

from django.test.utils import CaptureQueriesContext
from django.db import connection

with CaptureQueriesContext(connection) as queries:
    response = self.client.get(reverse("cours:liste"))

print(len(queries))

N’associez pas la qualité à un nombre arbitraire de requêtes : vérifiez que chaque requête est nécessaire et que le nombre ne croît pas avec le nombre d’objets.

Qualité automatique avec ruff

Ajoutez Ruff en dépendance de développement :

uv add --dev ruff
uv run ruff check .
uv run ruff format --check .

Vous pouvez corriger automatiquement le formatage :

uv run ruff format .

Un outil de qualité ne remplace pas les tests : il détecte surtout des problèmes de style, d’imports ou de constructions suspectes. Les tests ne remplacent pas non plus la revue de conception. Ils se complètent.

Une petite stratégie de test

Pour BiblioCours, commencez par les comportements risqués :

  • les cours brouillons ne sont jamais visibles publiquement ;
  • un slug inconnu renvoie 404 ;
  • un visiteur ne peut pas créer ou supprimer ;
  • les champs obligatoires sont refusés ;
  • le formulaire valide redirige après sauvegarde ;
  • la recherche ne provoque pas d’erreur avec une chaîne vide ;
  • les migrations partent d’une base vide.

Les tests de modèle peuvent vérifier les propriétés locales. Les tests de vue vérifient la route, le statut, le template et les données affichées. Les tests d’intégration plus larges servent pour les parcours critiques. N’écrivez pas un test séparé pour chaque ligne de code ; écrivez-en pour les contrats qui doivent rester vrais.

Exercices

  1. Ajoutez un test qui vérifie qu’un cours brouillon renvoie 404 sur sa page publique.
  2. Ajoutez un test POST valide qui vérifie la redirection et l’objet créé.
  3. Ajoutez un test POST invalide qui vérifie que la base ne contient aucun objet partiellement créé.
  4. Mesurez le nombre de requêtes de la liste pour 1 puis 20 cours et corrigez une éventuelle croissance N+1.
